# План MVP

## Границы

Одна площадка (Wildberries), четыре продавца, одна категория, фиксированный набор
ограничений. Без кросс-площадочного матчинга, без канонических моделей, без
уведомлений.

Цель MVP — доказать, что данные добываются стабильно и фильтр даёт осмысленную
выдачу. Всё остальное — после.

## Этапы

### Этап 0. Разведка API — **текущий**

Прогнать `python -m wb_aggregator.probe` с машины, у которой есть доступ к wb.ru,
и заполнить TODO в `wb_aggregator/config.py`.

Probe отвечает на пять вопросов:

1. Какой хост поиска живой и в какой обёртке приходит ответ.
2. `supplierId` для четырёх продавцов.
3. Имя рабочего параметра фильтра по продавцу (`fsupplier` / `supplier`) и по цене
   (`priceU` / `price`); не протекают ли посторонние результаты.
4. Реальный потолок глубины пагинации и максимальный размер страницы.
5. Отдаёт ли `card.wb.ru` структурированные характеристики.

**Готово, когда:** все TODO в `config.py` заполнены реальными значениями.

**Риск.** Если по п. 5 характеристик в карточке нет, RAM и SSD придётся тянуть из
basket-CDN (`basket-XX.wbbasket.ru/.../card.json`). Это заметно увеличивает объём
работы на этапе 2 — заложить запас.

### Этап 1. Коннектор

- `transport.py`: сессия, заголовки, rate limit, бэкофф на 429 и 5xx, ретраи.
- `connector.py`: `resolve_sellers`, `discover_filters`, `build_query`,
  `iterate_listings`, `fetch_details`.
- Сохранение сырых ответов на диск или в таблицу.

**Готово, когда:** полный обход по четырём продавцам отрабатывает без блокировок
и пишет сырые ответы.

### Этап 2. Нормализация — **частично сделано**

- `normalize.py` с `parse_price`, `parse_specs`, `check` — готово, покрыто
  фикстурой в `tests/test_normalize.py`.
- Осталось: разбор структурированных характеристик из реальной карточки, когда
  станет известен их формат (зависит от этапа 0, п. 5).
- Расширить фикстуру реальными названиями из первого обхода. Синтетические кейсы
  ловят не всё.

**Готово, когда:** на выборке из 100 реальных карточек доля `needs_review` ниже 10%.

### Этап 3. Хранение и история

- PostgreSQL: `listing`, `price_snapshot`, `raw_response`.
- Дедупликация снимков: новая строка только при изменении `price_effective`.
- Планировщик: обход раз в 3–6 часов.

**Готово, когда:** неделя непрерывной работы без ручного вмешательства.

### Этап 4. Выдача

Минимальный интерфейс: список подходящих ноутбуков с ценой, продавцом,
характеристиками и ссылкой. График истории цены по позиции.

## Критерии приёмки MVP

| Критерий | Порог |
|---|---|
| Соответствие ограничениям при ручной проверке 30 карточек | 100% |
| Доля детальных карточек, отсеянных на client-side фильтре | ≤ 20% |
| Позиции с неизвлечёнными RAM/SSD (`needs_review`) | ≤ 10% |
| Расхождение `выгружено` и заявленного `total` | 0 |
| Полный обход укладывается в окно, без блокировок | да |

Порог 20% по client-side отсеву относится к характеристикам. Отсев по цене должен
быть близок к нулю, так как площадка фильтрует по той же цене, что и мы; если он
растёт — семантика фильтра изменилась.

## Что осознанно не делаем в MVP

- Кросс-площадочный матчинг и канонические модели.
- Уведомления и подписки.
- Оценку «дорого / рынок / выгодно».
- Обработку вторичного рынка и состояния товара.
- Веб-интерфейс сверх минимального списка.

## Блокирующий пункт вне разработки

Проверить пользовательское соглашение Wildberries и возможности официального
Public API до того, как сервис станет публичным. См.
[02-wb-connector-spec.md](02-wb-connector-spec.md), п. 10.
