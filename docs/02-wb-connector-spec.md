# Спецификация коннектора Wildberries

## 1. Область

Один источник (Wildberries), четыре продавца, категория «ноутбуки».

Задача коннектора — вернуть только карточки, удовлетворяющие ограничениям,
максимально переложив фильтрацию на сторону площадки.

## 2. Модель ограничений

```
SearchConstraints:
  category:      "ноутбуки"
  sellers:       [ХОЛОДИЛЬНИК.РУ, ОНЛАЙНТРЕЙД.РУ, СИТИЛИНК, М.ВИДЕО]
  price_max:     50 000 RUB
  ram_min_gb:    16
  storage_min_gb: 1000        # 1 ТБ; порог 1000, чтобы не терять «1000 ГБ»
  storage_type:  SSD
  region:        <dest>
```

Реализация — `wb_aggregator.config.Constraints`.

## 3. Разделение фильтров

### A. Точно уходит в запрос

- **Продавец.** Один запрос на продавца, не общий (см. п. 5).
- **Цена.** Диапазон `0 … 50000` в копейках. Площадка фильтрует по той же
  минимальной цене, которую мы считаем эффективной, поэтому запас не нужен и
  `client_price_max == server_price_max`.
- **Категория / поисковый запрос.**

### B. Уходит, если удалось разрезолвить фасеты

- **RAM и объём накопителя.** Числовые id значений различаются между категориями
  и меняются со временем. Перед обходом выполняется `discover_filters`: запрос
  эндпоинта фильтров для категории и продавца, нормализация значений к гигабайтам,
  отбор всех значений ≥ порога.
- Если фасет не найден или маппинг не сложился — деградация в client-side
  с записью warning-метрики.

### C. Только client-side

- **Тип накопителя SSD** — часто указан только в характеристиках или названии.
- **Проверка, что «1 ТБ» — основной накопитель**, а не карта памяти или суммарный
  объём.

### Правило

Результат отбора всегда перепроверяется на клиенте по нормализованным
характеристикам, даже если фильтр ушёл в запрос. Server-side — оптимизация
трафика, а не источник истины.

Client-side проверка цены остаётся как ассерт: если она начинает срабатывать,
значит площадка поменяла семантику фильтра, и это повод разбираться.

## 4. Интерфейс

```python
class MarketplaceConnector:
    def resolve_sellers(names) -> list[SellerRef]: ...      # разово, кэшируется
    def discover_filters(category, seller) -> FilterSchema: ...
    def build_query(constraints, schema) -> QuerySpec: ...
    def iterate_listings(spec) -> Iterator[RawListing]: ...
    def fetch_details(nm_id) -> RawCard: ...
```

Поток:

```
resolve_sellers
  -> для каждого продавца: discover_filters -> build_query
  -> постраничный обход
  -> предфильтр по данным листинга
  -> fetch_details только для выживших
  -> нормализация
  -> сохранение
```

Экономия — на последнем шаге: детальная карточка запрашивается только для
кандидатов.

## 5. Стратегия обхода: per_seller или combined

Решается замером, но по умолчанию `per_seller`.

**Аргумент за раздельные запросы.** Лимит глубины пагинации почти всегда действует
на запрос, а не на клиента. Четыре отдельных запроса дают 4×N доступной глубины
вместо N. Объединение — единственный сценарий, где можно упереться в потолок и
молча потерять товары: API вернёт 200 и пустую страницу, а не ошибку.

**Экономия при объединении почти нулевая.** Число страниц ≈ общее количество
результатов / размер страницы и не зависит от разбиения. Объединение экономит
только неполные хвостовые страницы — три запроса за цикл.

**Что теряется при объединении:**

- падение на середине выдачи роняет всех четырёх продавцов;
- нет метрик и алертов в разрезе продавца;
- нельзя развести продавцов по разной частоте обхода;
- фасеты резолвятся для объединённого набора, маппинг усложняется.

С текущими ограничениями (ноутбуки до 50к, 16 ГБ RAM, SSD от 1 ТБ, четыре
продавца) речь идёт о десятках, максимум паре сотен позиций — до лимита глубины
не дойти ни в одном варианте. Вопрос чисто эксплуатационный, и там раздельные
запросы выигрывают.

```python
QueryStrategy:
    seller_batching: per_seller | combined
    page_size:            # из probe
    max_depth:            # из probe
    split_on_depth_limit: True   # если total > page_size*max_depth,
                                 # дробить по ценовым поддиапазонам
```

`split_on_depth_limit` пишется один раз и понадобится при снятии порога 50к или
добавлении пятого продавца.

Обязателен алерт при `выгружено < total` — это тихий сбой, который иначе
обнаружится через месяц по недостающим товарам.

## 6. Извлечение характеристик

Источники по убыванию надёжности: структурированные характеристики карточки →
название → описание. Каждому полю проставляется `source` и `confidence`.

Если RAM или SSD не извлеклись ни из одного источника — товар уходит в
`needs_review`, а не молча отбрасывается.

Реализация — `wb_aggregator.normalize.parse_specs`.

## 7. Подводные камни

- **Регион.** Цена и наличие зависят от `dest`. Для MVP фиксируется один регион.
- **1 ТБ ≠ 1000 ГБ.** Нормализатор приводит «1 ТБ», «1024 ГБ», «1000 ГБ» к единой
  шкале; порог задан явно как 1000, чтобы не терять модели с «1000 ГБ».
- **Продавец в карточке.** Название в выдаче может отличаться от юрлица.
  Матчинг по `supplierId`, не по строке.
- **Пагинация.** Ограничение глубины; при большом числе результатов запрос
  дробится по подкатегориям или ценовым поддиапазонам.
- **Формат ответа.** Встречаются обёртки `{"products": []}` и
  `{"data": {"products": []}}`, а также два формата цены: v18
  (`sizes[].price.{basic,product}`) и старый (`priceU` / `salePriceU`).
  Парсер поддерживает оба.


## 9. Нефункциональные требования

- Один воркер на продавца, последовательные запросы с паузой; конфигурируемый
  rate limit и экспоненциальный бэкофф на 429 и 5xx.
- Обход раз в 3–6 часов, полный раз в сутки.
- Контрактные тесты на структуру ответа плюс алерт при падении доли успешно
  распарсенных карточек ниже порога — первый признак смены формата.

## 10. Правовая оговорка

Используемый API — внутренний, недокументированный, без гарантий стабильности.
Автор одной из публичных статей по теме прямо оговаривает, что примеры даны в
образовательных целях, а для коммерческой работы у Wildberries есть официальный
Public API (dev.wildberries.ru).

Для разведки и MVP внутренний API — рабочий путь. **До того, как сервис станет
публичным, нужно проверить, покрывает ли официальный API сценарий, и уточнить
условия пользовательского соглашения.** Это блокирующий пункт, не пожелание.
