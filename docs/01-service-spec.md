# Спецификация сервиса

Статус: черновик. Описывает целевое решение целиком; MVP покрывает малую его часть
(см. [03-mvp-plan.md](03-mvp-plan.md)).

## 1. Цель

Собирать объявления и товарные карточки ноутбуков с нескольких площадок, приводить
их к единому виду и давать сквозной поиск, сравнение цен и историю изменений.

## 2. Источники данных

Для каждой площадки — отдельный коннектор с единым интерфейсом.

- **Официальный API или партнёрский фид** — приоритетный способ.
- **HTML-парсинг или внутренний JSON API** — фолбэк там, где официального API нет.
  Требует проверки robots.txt, лимитов частоты и пользовательского соглашения
  площадки. Часть площадок явно запрещает автоматический сбор; это нужно закрыть
  до запуска, а не после.

Коннектор отдаёт «сырое» объявление плюс метку источника, время сбора и исходный URL.

Кандидаты после MVP: Ozon, Яндекс Маркет, DNS, Citilink, Avito.

## 3. Ключевая техническая проблема: нормализация и матчинг

Одна и та же модель на разных площадках называется по-разному:
«Lenovo IdeaPad 5 15IAL7», «Ноутбук Lenovo IdeaPad 5 15.6" i5 16/512»,
«IdeaPad5-15 82SF».

Нужен слой, который из заголовка и характеристик извлекает:

- бренд, линейку, модельный код;
- CPU, объём RAM, тип и объём накопителя, GPU, диагональ и разрешение экрана;
- состояние (новый / б/у / витрина), комплектность, регион.

Подход: правила и словари закрывают основную массу случаев, эмбеддинги или
LLM-классификатор — остаток, спорные матчи уходят на ручную модерацию.
Метрика качества — точность привязки к канонической карточке.

## 4. Модель данных

| Сущность | Назначение |
|---|---|
| `CanonicalModel` | каноническая модель: бренд, код, спецификации |
| `Listing` | конкретное объявление: источник, внешний id, URL, цена, состояние, продавец, регион, статус, ссылка на `CanonicalModel` |
| `PriceSnapshot` | цена объявления на момент времени |
| `Seller` | продавец: рейтинг, тип (частник / магазин) |
| `MatchCandidate` | неуверенные привязки для ручной проверки |

### Цена

Цена — вычисляемая величина, не одно поле.

```
price_effective = min(все непустые ценовые варианты карточки)
```

Хранятся:

- `price_effective` — каноническая цена; по ней фильтр, сортировка и история;
- `price_effective_kind` — какой вариант выиграл (базовая, со скидкой, с кошельком);
- `prices_raw` — все варианты как пришли, без интерпретации.

Метка и сырьё нужны для интерпретации истории: без них скачок цены неотличим от
ситуации, когда площадка перестала отдавать один из вариантов.

При вычислении минимума отсекаются `null`, `0` и подозрительно малые значения
(порог `MIN_PLAUSIBLE_PRICE_RUB`) — это обычно артефакты вроде цены аксессуара.

## 5. Архитектура

```
планировщик
   -> очередь задач
   -> коннекторы (пул прокси, rate-limit на домен)
   -> нормализация
   -> дедупликация
   -> хранилище (PostgreSQL + поисковый индекс)
   -> внутренний API
   -> веб-интерфейс
```

Отдельно: воркер алертов, воркер аналитики цен, админка модерации матчей.

## 6. Функциональность

- Поиск и фильтры по спецификациям, цене, состоянию, региону, площадке.
- Карточка модели со всеми предложениями и минимальной ценой.
- История цен и график (по `price_effective`).
- Оценка «дорого / рынок / выгодно» относительно медианы по модели за период.
- Подписки и уведомления по фильтру.
- Отметка исчезнувших объявлений. Важно: пропало ≠ продано.

## 7. Нефункциональные требования

- Периодичность обхода: популярные запросы раз в 1–3 часа, длинный хвост раз в сутки.
- Порядок объёмов для оценки: сотни тысяч активных объявлений, миллионы снимков цен.
- Устойчивость к смене формата: контрактные тесты на структуру ответа плюс алерт
  при падении доли успешных парсингов.
- Хранение сырых ответов N дней для переразбора без повторного сбора.
- Дедупликация снимков: новая строка только при изменении `price_effective`.

## 8. Открытые вопросы

- Фокус: новые устройства из ритейла или вторичный рынок. От этого зависит
  сложность матчинга и юридическая часть.
- Юридический статус сбора по каждой площадке.
- Нужен ли пользователям кросс-площадочный матчинг с первого релиза или достаточно
  поиска внутри одной площадки.
